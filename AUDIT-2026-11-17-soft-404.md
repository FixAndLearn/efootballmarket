# Site audit — the soft-404 defect

Status: **fixed, deployed, verified live.** Commit `d1b977f`, deploy
`dpl_4EtV3Zo5YQFDKaf2UBstSYYz76Nw`.

## What was wrong

Every dynamic route that called `notFound()` answered **HTTP 200** for content
that did not exist:

| URL | before | after |
|---|---|---|
| `/listings/<malformed>` | 200 | **404** |
| `/listings/<random uuid>` | 200 | **404** |
| `/news/<bogus>` | 200 | **404** |
| `/u/<bogus>` | 200 | **404** |
| `/pay/<bogus>` | 200 | **404** |
| `/orders/<bogus>` | 200 | 307 → login (door guarded before lookup) |
| `/orders/<bogus>/chat` | 200 | 307 → login |

URLs that matched no route (`/middleman`, `/a-route-that-never-existed`) already
returned a correct 404 — that asymmetry is what pointed at the cause.

## Root cause

A `loading.tsx` does more than show a spinner: it wraps the segment in a
Suspense boundary, and Next commits the status line and headers as soon as that
boundary suspends. `notFound()` works by *throwing*, so if the throw arrives
after the commit there is no status left to change — the visitor sees the right
words, a crawler sees a healthy indexable page.

The app had four `loading.tsx` files, one at the root:

```
src/app/loading.tsx                              <- applied to EVERY route
src/app/(marketplace)/listings/[id]/loading.tsx
src/app/(marketplace)/orders/[id]/loading.tsx
src/app/(marketplace)/browse/loading.tsx         <- harmless, no notFound()
```

The root one meant **no route in the app could 404 on missing content.**

Proof it was the boundary: served HTML for one nonexistent listing contained
both the root `Loading...` fallback and the `Page or Squad Not Found` body in the
same response.

## Two dead ends (recorded so they are not retried)

1. **Move `notFound()` into `generateMetadata`.** Correct in principle, and it is
   still in place (`2e93888`), but on its own it changed nothing — the root
   boundary still committed before metadata resolution.
2. **Re-throw `NEXT_` digests from the metadata `try/catch`.** Also correct, and
   also still in place (`af33ac2`), because the existing bare `catch { return
   { title: ... } }` was swallowing the signal. Again no change on its own.

Both were real bugs worth fixing, but neither addressed the flush. Only removing
the boundaries did. **Lesson: verify against a live build, not against a commit.**

## The fix

- Deleted the three `loading.tsx` boundaries (kept `browse/loading.tsx`).
- `tournaments/host` and `tournaments/register` are client components calling
  `useSearchParams()` and were silently relying on the root boundary — deleting
  it broke the build with `prerender-error`. Each now wraps its own body in
  `Suspense`. This is why the deletion could not be blind.
- Root `layout.tsx` hardcoded `robots: { index: true, follow: true }`, inherited
  by the not-found branch, so every 404 emitted `noindex` **and**
  `index, follow`. Removed the inherited pair; kept the `googleBot` hints.
- `sitemap.ts` `revalidate` 3600 → 300 so archived listings age out faster.

## Also fixed in this pass

Archived/sold listings were **indexable and described themselves as buyable**.
`/listings/dc47d722` is `status='archived'` in the DB yet served 200,
`index, follow`, and a description reading *"Buyer protection applies to orders
from this published listing"* — false. Those pages still resolve for old links
and receipts, but are now `noindex` and say the squad is no longer available.
It now 404s outright, because the metadata layer throws before the body is
reached.

## Verified live after deploy

- 6 bogus-content routes 404 (table above); 404 body is the real branded
  `not-found.tsx`, not a bare Next error
- exactly one robots tag per response: `noindex` on 404s, `index, follow` on
  published listings, none (= indexable) elsewhere
- sitemap: 70 URLs, **all 200**, archived listing no longer present
- 69 unique internal links crawled from 7 key pages: **all 200**
- homepage still SSRs its live metrics (23 / 5 / 61 / 2)
- `/browse` still SSRs 23 listing links
- TTFB 0.15s–1.1s across the checked routes — no regression from the deletion

## Still open (not touched this pass)

- `/tournaments` renders `Loading brackets...` into the served HTML and fills in
  client-side. Content does arrive for real users; it is a SSR/SEO weakness, not
  a break. Bigger change than a metadata pass.
- Sitemap responds in ~1s (DB query per request at `revalidate=300`). Fine, but
  on-demand revalidation on publish/archive would be better than any TTL.
- 9 bare `catch {}` blocks elsewhere in `src/` — same shape as the bug above.
  Worth a sweep; each one could be silently discarding a redirect or 404.
